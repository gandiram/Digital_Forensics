Understanding File Systems

A file system is the map that turns "a file called report.docx" into "these particular blocks on this particular disk". Understanding the map is what lets you find things the map no longer mentions.

1.1

Sectors, clusters and why the difference matters

Before clusters, know the physical vocabulary. Disk drives are made of one or more platters coated with magnetic material:

ComponentMeaning
GeometryA disk's logical structure of platters, tracks and sectors.
HeadThe device that reads and writes data. There are two heads per platter, for the top and bottom sides.
TracksConcentric circles on a platter where data is located.
CylindersA column of tracks on two or more platters.
SectorsA section on a track, usually 512 bytes.

To find the total number of addressable bytes, multiply cylinders × heads × sectors. Vendors call this the cylinder, head and sector (CHS) calculation.

The operating system does not allocate single sectors — that would make the allocation table enormous. Instead it groups sectors into clusters, also called allocation units, and allocates whole clusters at a time.

The consequence is immediate and is the reason half of forensic recovery is possible: a file almost never fills its last cluster exactly, and whatever occupied that space before is still sitting there.

Drive slack, RAM slack and file slack — the exact terms

Microsoft operating systems allocate disk space by clusters, and this produces drive slack: the unused space in a cluster between the end of an active file's content and the end of the cluster. Drive slack is made up of RAM slack and file slack.

The textbook's worked example. A text document of 5000 characters is saved on a FAT16 1.6 GB disk. The OS reserves one cluster automatically — about 32,768 bytes, or 64 sectors. The 5000 bytes occupy 10 sectors (5120 bytes), so 120 bytes of that tenth sector are unused: that is the RAM slack — the portion of the last sector used in the last assigned cluster. The remaining 54 sectors, about 27,648 bytes, are the file slack.

On older Microsoft systems, DOS had to write in full 512-byte sectors, and the data used to fill that 120-byte void was pulled from RAM — so anything in memory at that moment, such as logon IDs or passwords, was written into RAM slack. On newer Windows systems the RAM slack is zeroed out and contains no RAM data. File fragments, deleted e-mails and passwords are still often found in file slack.

Example — the resignation letter nobody saved

An employee types a resignation letter, prints it and deletes the file. Months later the cluster that held it is partly reused by a 2 KB configuration file. The configuration file occupies the first 2 KB of the cluster; the remaining 2 KB — the file slack — still contains the middle of the resignation letter. A keyword search across slack space finds it. The user deleted the file, the operating system reused the space, and the text survived anyway.

1.2

Understanding disk drives — the five terms

Disk drives are made up of one or more platters coated with magnetic material. You are expected to know these five components:

TermMeaning
GeometryA disk's logical structure of platters, tracks and sectors.
HeadThe device that reads and writes data. There are two heads per platter, for the top and bottom surfaces.
TracksConcentric circles on a platter where data is located.
CylindersA column of tracks on two or more platters.
SectorsA section on a track, usually 512 bytes.

To find the total number of addressable bytes on a disk, multiply cylinders × heads × sectors per track × bytes per sector. Newer Advanced Format (4K) disks use 4096-byte sectors instead.

1.3

Solid-state storage — wear-levelling and the garbage collector

Flash storage in USB drives, laptops, tablets and phones is a challenge for examiners, because if deleted data is not recovered immediately it might be lost forever. The reason is a feature every flash device has: wear-levelling.

On a magnetic drive, deletion removes only the references and leaves the original data in unallocated space, so recovery is a matter of copying that space. Solid-state systems behave differently: memory cells continuously shift data at the physical level to other cells that have had fewer reads and writes, so that all cells wear evenly. Cells are designed to perform only 10,000 to 100,000 reads and writes depending on the manufacturer; once they reach that limit they can no longer retain data, and you get an access failure message when you try to connect. All of this is controlled by the firmware on the flash device.

The garbage collector — why the evidence disappears on its own

When data is rotated to another memory cell, the old cell addresses are listed in a firmware file called the "garbage collector". At some point the drive's firmware erases the data in those unallocated cells by overwriting the value 1 in every cell on that list.

This happens inside the drive, on the firmware's own schedule, with no involvement from the operating system — which is why a write-blocker cannot prevent it. The practical rule follows directly: when dealing with solid-state devices, make a full forensic copy as soon as possible, in case you later need to recover data from unallocated space. Delay is the one thing that guarantees loss.

1.4

What deletion actually does

This is the single most important idea in the unit. When a user deletes a file, the operating system does not erase the data. It performs two cheap bookkeeping operations:

  1. It marks the directory entry as unused — in FAT by overwriting the first character of the file name with the byte E5h; in NTFS by clearing the "in use" flag in the MFT record.
  2. It marks the clusters as free in the allocation table, so they become available for reuse.

The file's actual bytes are untouched and remain on the disk until something else happens to be written over them. That is why recovery works, and why the honest answer to "is it recoverable?" is always "it depends how much the disk has been used since".

Why this answer differs on solid-state media

On a magnetic hard disk the data survives until something overwrites it. On flash media, wear-levelling moves data between cells and the firmware's garbage collector erases the vacated cells on its own schedule — so deleted data can vanish without the operating system doing anything, and a write-blocker cannot prevent it. State this limitation in an examination answer rather than claiming deleted data is always recoverable. The modern TRIM command is the operating system's way of telling the controller which blocks are free, which accelerates the same process.

Exploring Microsoft File Structures

FAT is old, simple and still everywhere — on USB sticks, camera cards and the EFI partition of every modern PC. Its simplicity is what makes it the best place to learn how deletion and recovery actually work.

2.1

Disk partitions and the partition gap

Many hard disks are partitioned — divided into two or more sections. A partition is a logical drive. Windows can have three primary partitions followed by an extended partition that can contain one or more logical drives.

Someone wanting to hide data can create hidden partitions, or voids — large unused gaps between partitions. This unused space between partitions is called the partition gap. It is possible to create a partition, add data to it, and then remove the references so that Windows no longer shows it; if data is hidden in the partition gap, a disk editor can still reach it.

Another technique is to hide incriminating evidence at the end of a disk by declaring a smaller number of bytes than the actual drive size. Disk-editing tools such as WinHex or Hex Workshop let you access these hidden or empty areas, and they show file headers and the key hexadecimal codes the operating system uses to identify and maintain the file system. The partition table itself records a hexadecimal code identifying each file system — for example 01 for DOS 12-bit FAT.

The examiner's rule for partitions

Account for every sector on the disk. Add the sizes of the partitions you can see and compare the total against the drive's actual capacity. A gap means either a partition gap or a deliberately shortened declaration — and both are places data hides. This is a mechanical check that takes a minute and is frequently skipped.

2.3

The E5h marker — deletion in one byte

FAT — the File Allocation Table — is the file structure database Microsoft originally designed for floppy disks. It organises files so the OS can find them, and is typically written to a disk's outermost track. It contains filenames, directory names, date and time stamps, the starting cluster number, and file attributes (archive, hidden, system and read-only). Linux and macOS can also format, read and write FAT devices such as USB drives and SD cards.

In FAT, a directory entry stores the file name, attributes, timestamps, starting cluster and size. When the file is deleted, the system replaces only the first character of the name with the hexadecimal byte E5 and frees the cluster chain. Everything else in the entry survives.

Example — recovering the file by hand

Because the entry still records the starting cluster and the size, recovery is often trivial: read that many bytes beginning at that cluster. Tools do it automatically, and this is exactly what "undelete" meant in the DOS era. The catch: the FAT chain is gone, so if the file was fragmented across non-adjacent clusters, you get the first fragment cleanly and must carve the rest. That is why you always report recovered files as "recovered" and check them for truncation before relying on their content.

Examining NTFS Disks

NTFS has been the Windows file system since Windows NT and is what you will meet on virtually every seized PC. It is far richer than FAT — and every extra feature is an extra place for evidence to survive.

3.1

The Master File Table

NTFS was introduced when Microsoft created Windows NT and remains the main Windows file system. Its design was partially based on HPFS — the High Performance File System Microsoft built for IBM's OS/2, and early NT could read OS/2 HPFS drives; that backward compatibility ended with Windows 2000.

NTFS was Microsoft's move toward a journaling file system: it keeps track of transactions such as deleting or saving a file, and records the transaction before the system carries it out, so that after a power failure the system can either complete the transaction or return to the last good setting.

NTFS takes an idea to its logical conclusion: everything written to the disk is considered a file. On an NTFS disk the first data set is the Partition Boot Sector, which starts at sector 0 and can expand to 16 sectors; immediately after it comes the Master File Table (MFT). In the MFT, the first 15 records are reserved for system files, and records in the MFT are called metadata.

Two advantages over FAT worth stating in an answer

Much less file slack. NTFS uses a 4 KB cluster for every drive size from 7 MB right up to 2 TB, and only at 16 TB and beyond does it grow to 8 KB and larger. Smaller clusters on small drives means less wasted slack — which saves space on every NTFS disk.

Unicode. NTFS (and VFAT, for long filenames) uses Unicode rather than the 8-bit ASCII configuration — UTF-8, UTF-16 or UTF-32. For Western alphabetic characters UTF-8 is identical to ASCII. This matters directly when you run keyword searches on a drive: a term stored as UTF-16 will not match an ASCII search pattern, which is a common reason a search "finds nothing".

3.2

Resident data — the file inside its own record

In the NTFS MFT, all files and folders are stored in separate records of 1024 bytes each. Each record contains file or folder information divided into record fields holding metadata and the file's data — or links to it. A record field is referred to as an attribute ID.

Information is stored in one of two ways. For very small files — about 512 bytes or less — all file metadata and data are stored in the MFT record itself. These are called resident files. Files larger than 512 bytes are stored outside the MFT; the record then provides the cluster addresses where the file lives on the partition, and those cluster addresses are called data runs. Such a record is non-resident.

Reading an MFT record in a hex editor

Each MFT record starts with a header identifying it as a resident or non-resident attribute, and the first four characters of every MFT record are FILE. The data is displayed in little endian format — read from right to left — so the hexadecimal value 0x400 appears on screen as 00 04 00 00, and 0x40000 as 00 00 04 00.

OffsetField
0x00The MFT record identifier FILE — the letter F sits at offset 0.
0x14Length of the header, which indicates where the next attribute starts; typically 0x38 bytes.
0x1C–0x1FSize of the MFT record; the default is 0x400 (1024) bytes, or two sectors.
0x32–0x33The update sequence array, storing the last 2 bytes of the first sector of the record.

Example — the note that carving would never find

A suspect writes a 300-byte text file containing a bank account number and deletes it. Because it was resident, the content lived entirely inside its MFT record and never touched a data cluster. A tool that only carves unallocated space finds nothing. A tool that parses the $MFT and reads unallocated MFT records recovers the text in full. This is a concrete case where using two different techniques produces two different answers — and why "we found nothing" must always be qualified by "using this method".

3.3

Alternate Data Streams

Alternate data streams are ways data can be appended to existing files. In NTFS an alternate data stream becomes an additional file attribute and allows the file to be associated with different applications — so it remains one data unit. Microsoft's own documented example: a graphics program can store a thumbnail image of a bitmap in a named data stream within the NTFS file containing the image.

The stream is defined in the MFT by the colon between the file extension and the stream label. Streams are invisible to Explorer and to a plain dir, and the file's reported size does not change. The two commands the book gives for creating one:

A useful property for the examiner

Alternate data streams are an NTFS feature. Copy the file to a FAT32 USB stick or e-mail it, and the hidden stream is silently lost — which is why the technique is used for local concealment rather than for moving data out. Windows itself uses ADS legitimately: the Zone.Identifier stream is what records that a file came from the internet, and it is itself useful evidence of a download.

3.4

NTFS compressed files

NTFS provides compression to improve data storage. With NTFS you can compress files, folders or entire volumes; with FAT16 you can compress only a volume. Compressed data is displayed normally in Explorer and in applications such as Word, so a user may not know it is compressed.

In an investigation you typically work from an image of the compressed disk, folder or file. Most forensics tools can uncompress and analyse compressed Windows data, including the Lempel-Ziv-Huffman (LZH) algorithm and formats such as PKZip, WinZip and GNU gzip.

Where the tools stop

Forensics tools might have difficulty with third-party compression utilities such as the .rar format. If you identify third-party compressed data, you must uncompress it with the utility that created it — and record that you did so, because you have used a non-forensic tool on evidence.

3.5

The Encrypting File System and the Recovery Key Agent

With Windows 2000 Microsoft added optional built-in encryption to NTFS called EFS — Encrypting File System. EFS uses public key and private key methods to encrypt files, folders or disk volumes, and only the owner or user who encrypted the data can access it. The owner holds the private key; the public key is held by a certification authority such as a network server or a company like VeriSign. Windows decrypts the data automatically when the user or an application accesses it.

A recovery certificate is generated and sent to the Windows administrator account, so that files can still be recovered if there is a problem with the user's original private key. Where the recovery key goes depends on the setting: for a network user it is sent to the local domain server's administrator account; on a stand-alone workstation it goes to the local administrator account.

The Recovery Key Agent implements that certificate. Administrators can recover a key through Windows or from a command prompt, using two commands: cipher and copy.

PointDetail
cipherWorks only on NTFS running Windows 2000 Professional or later — encrypted files are not part of FAT12, FAT16 or FAT32.

cipher /wOverwrites all deleted files, making them impossible to recover with data recovery or forensic carving tools. An anti-forensic capability built into Windows itself.
The behaviour that gives the examiner a way in

If an encrypted file is copied from an EFS-enabled NTFS disk or folder to non-EFS storage media or a folder, it is decrypted automatically. A suspect who copies an encrypted file to a FAT USB stick has handed you the plaintext. The same fact explains innocent-looking decryptions: users frequently defeat their own encryption without realising it.

3.6

Deleting NTFS files — and the Info2 file

There are two routes, and they behave differently:

  1. Deleting in File Explorer — Windows renames the file and moves it to a subdirectory with a unique identity in the Recycle Bin. It then stores the original path and filename in the Info2 file, the control file for the Recycle Bin, which contains ASCII data, Unicode data, and the date and time of deletion for each item.
  2. Deleting with the del command — this does not rename the file or move it to the Recycle Bin. It eliminates the file from the MFT listing in the same way FAT does.

When a file is deleted at a command prompt — or when the user empties the Recycle Bin — the associated clusters are designated as free, and the $Bitmap file is updated to mark them available for new data.

Why Info2 is worth finding

The file in the Recycle Bin has been renamed, so its name no longer tells you anything. Info2 is what restores the original path, the original filename and the exact deletion time — which is often the single most useful timestamp in a case, because it dates the suspect's decision to get rid of something.

3.7

The Resilient File System (ReFS)

With Windows Server 2012 Microsoft created a new file system, ReFS, designed to address very large data storage needs such as the cloud. Three features were incorporated into its design: maximised data availability, improved data integrity, and scalability.

ReFS is an outgrowth of NTFS. It is intended only for data storage and cannot be used as a boot drive, and only Windows 8/8.1 and later and Windows Server 2012 and later can access ReFS drives. It uses disk structures similar to the MFT, and its storage engine uses a B+-tree sort method for fast access to large data sets.

Allocate-on-write — why ReFS is friendly to an examiner

ReFS uses allocate-on-write, which copies updates of data files to new locations rather than overwriting the original — similar to shadow paging. The purpose is recoverability: if a failure occurs during the write, the original can be recovered easily.

The forensic consequence follows immediately: an update does not destroy the previous version, so earlier states of a file may still be present on the volume. The file system's integrity feature is, incidentally, an evidence-preservation feature.

3.8

Timestamps — MACE and the $STANDARD_INFORMATION trap

NTFS keeps four timestamps per file, remembered as MACE: Modified, Accessed, Created, Entry modified. Crucially it keeps them twice — once in the $STANDARD_INFORMATION attribute and once in $FILE_NAME.

Timestomping, and how it is detected

Anti-forensic tools alter timestamps to disguise when a file appeared. They typically change only $STANDARD_INFORMATION, because that is the set Explorer displays and the set the Windows API exposes. The $FILE_NAME copy is updated by the file system itself and is much harder to forge. A file whose two timestamp sets disagree has almost certainly been tampered with — and a creation date earlier than the volume's own creation date is an obvious impossibility. Comparing the two sets is a standard check.

Understanding Whole Disk Encryption

Whole disk encryption exists because of theft. Loss of personally identifiable information (PII) and trade secrets through computer theft has become a serious concern, and it changes the fundamental assumption of disk forensics: that a powered-off drive can be imaged and read later.

4.1

What it does, and why it defeats the classic procedure

Why it was adopted. Company PII might be employees' full names, home addresses and identity numbers — enough for a criminal to open credit accounts in their names. Trade secrets are any information a business keeps confidential because it gives a competitive edge, and an inadvertent release can devastate that edge. Theft of laptops and handheld devices is the particular concern: if the data is not secured, the owner may be liable for damages such as stolen identities or credit card fraud. Many jurisdictions now require anyone losing such data to notify potential victims as soon as possible.

Why it exists. Loss of personally identifiable information (PII) and trade secrets through computer theft is a growing concern. PII might be employees' full names, home addresses and identity numbers — enough for a criminal to open credit accounts in their names. A trade secret is any information a business keeps confidential because it gives a competitive edge, and its inadvertent release can devastate that edge. Theft of laptops and handheld devices is the particular worry, and if the data is not secured the owner may be liable for the resulting damages. Many jurisdictions now require notifying potential victims as soon as possible, which is why vendors added whole disk encryption — and why it creates new challenges in examining and recovering data.

Full-disk encryption encrypts every sector of the volume. Only when the correct key is supplied at boot does the content become readable. The classic static procedure — seize, power down, image the drive, examine at leisure — produces a perfectly valid image of ciphertext.

A note on the trend: with improved encryption methods, extracting digital evidence becomes steadily more difficult. That is precisely why the ability to make remote and live acquisitions has moved from a specialism to a core skill.

4.3

Where the key can legitimately come from

The recovery key

BitLocker recovery keys are frequently escrowed — in a Microsoft account, in Active Directory, or in Azure AD. In a corporate case the organisation may simply hold the key, and a request to the IT department is the fastest route.

A live acquisition

If the machine is found running and unlocked, the volume is mounted and readable. Imaging it live captures plaintext. Powering it off destroys that opportunity permanently.

Memory capture

The encryption key resides in RAM while the volume is mounted. A RAM capture taken before shutdown may allow key recovery with tools such as Volatility.

The passphrase

Lawfully obtained from the user, or found written down, stored in a browser, or present in another device's backup.

The rule that reverses classic training

Traditional teaching says: pull the plug to avoid altering the disk. With whole-disk encryption, pulling the plug can destroy your only access to the evidence. Current practice at a scene is to check first whether encryption is active and the volume is mounted; if it is, perform a live acquisition and a RAM capture before shutting anything down. Document the decision and the reason — you are deliberately accepting some alteration of the running system in exchange for obtaining readable evidence at all.

Example — two officers, one laptop

A laptop is found switched on and logged in, with BitLocker enabled. Officer A follows the old rule, pulls the power and images the drive: the image is valid, verifiable and entirely unreadable. Officer B captures RAM, then images the mounted volume live, documenting each step: the evidence is readable and admissible, with the alterations recorded and explained. The same laptop yields everything or nothing depending on a decision made in the first two minutes.

Tool support has caught up

Modern suites handle encrypted volumes directly when a key is available — Autopsy added BitLocker support in version 4.22 (2025), so an examiner with the recovery key can mount and analyse the volume inside the tool rather than decrypting separately. Always record which key was used and where it came from; that provenance is part of the evidence.

The Windows Registry

The registry is a hierarchical database holding configuration for the operating system, the hardware, the installed software and every user account. For an examiner it is something more useful: a detailed record of what was connected, what was installed, what was opened and what was searched for.

5.1

Registry terminology — the words you are marked on

When Microsoft created Windows 95 it consolidated the initialization (.ini) files into the Registry, a database storing hardware and software configuration, network connections, user preferences — including usernames and passwords — and setup information. The major sections have been consistent since Windows 2000.

TermDefinition
RegistryA hierarchical database containing system and user information.
Registry EditorThe Windows utility for viewing and modifying Registry data. There are two: Regedit and Regedt32, the latter introduced with Windows 2000.
HKEYWindows splits the Registry into categories prefixed HKEY_. Windows 9x had six HKEY categories; Windows 2000 and later have five. Programmers refer to the "H" as the handle for the key.
KeyEach HKEY contains folders referred to as keys, which can contain other keys or values.
SubkeyA key displayed under another key — like a subfolder.
BranchA key and its contents, including its subkeys.
ValueA name and value within a key — similar to a file and its data content.
Default valueEvery key has one, which may or may not contain data.

A distinction worth getting right

A hive is not the same as an HKEY. HKEYs are the five categories you see in the Registry Editor; hives are the specific branches that are actually backed by files on disk. That is why an offline examination works with hive files, not with HKEYs — the HKEYs only exist once Windows has assembled them.

Real example — proving a specific USB stick was used on a specific PC

A design engineer is suspected of copying drawings to a personal USB stick. The stick is seized separately. Its serial number is read from the device itself, and the same serial number appears in USBSTOR on the office workstation, with first and last connection times. Neither artefact is on the USB stick; both are on the PC, and together they place that device, in that machine, at that moment.

How the registry is examined in practice

You do not open a suspect's registry in regedit on a running machine. You extract the hive files from the disk image and parse them offline. Several forensics tools have built-in or add-on Registry viewers — the textbook names X-Ways Forensics, OSForensics, Forensic Explorer and FTK — and RegRipper, Registry Explorer and the registry modules in Autopsy and AXIOM do the same job. Collect the .LOG transaction files alongside each hive; they can contain the most recent changes not yet written into the hive itself.

A typical request looks like this: the Legal Department asks you to search a raw dd image for any reference to e-mail addresses containing a particular name at a particular domain. You load the image, open that user's NTUSER.DAT, search the Registry, and add anything of interest to the case report you hand back. That is the whole workflow — and note that the deliverable is a report, not a screenshot.

Microsoft Startup Tasks

Anything that wants to survive a reboot must arrange to be started again. That requirement is what makes startup locations the first place an examiner looks for malware, keyloggers and remote-access tools.

6.1

Why startup matters to the evidence

The textbook's reason for studying startup is evidential, not technical. In some investigations you must preserve data on the disk exactly as the suspect last used it, and any access to the system after it was used for illicit purposes alters your disk evidence. Altering disk data lessens its evidentiary quality considerably, and accessing a suspect computer incorrectly could make the evidence corrupt and less credible for litigation.

There is a second, positive reason: knowing which files are accessed when Windows starts helps you determine when a suspect's computer was last accessed — which is particularly important with machines that may have been used after an incident was reported.

6.2

The six steps, and the BCD store

Any computer using NTFS performs the following steps when it is turned on:

  1. Power-on self test (POST)
  2. Initial startup
  3. Boot loader
  4. Hardware detection and configuration
  5. Kernel loading
  6. User logon

From Windows Vista onwards the boot process uses a boot configuration data (BCD) store. On BIOS-designed desktops and laptops a BCD registry file in the \Boot\Bcd folder controls the boot process. The BCD store replaced the Windows XP Boot.ini file.

The editor you must use — and the two you cannot

To access the BCD file you use the BCD Editor. Regedit and Regedt32 are not associated with this file, even though it is a registry file by format. Trying to reach boot configuration through the ordinary registry editors is a common and fruitless mistake.

Vista also moved to the Extensible Firmware Interface (EFI) alongside the older BIOS system — EFI boot firmware is designed to provide better protection against malware than BIOS does. The single Ntldr program that loaded the OS in Windows XP was replaced by three utilities:

UtilityRole
Bootmgr.exeThe Windows Boot Manager — controls boot flow and allows booting multiple operating systems.
Winload.exeThe OS loader — installs the kernel and the Hardware Abstraction Layer (HAL) and loads memory with the necessary boot drivers.
Winresume.exeRestarts the system after it goes into hibernation mode.
6.3

The Windows boot sequence in detail

  1. Firmware (UEFI or BIOS) performs the power-on self test and selects a boot device.
  2. The boot manager — bootmgfw.efi on UEFI systems, bootmgr on legacy BIOS — reads the BCD store to decide what to boot.
  3. The Windows loader winload.efi loads the kernel ntoskrnl.exe and the hardware abstraction layer, and reads the SYSTEM registry hive to find the drivers marked boot-start.
  4. Session Manager smss.exe initialises the environment and creates the page file.
  5. Winlogon presents the logon screen; lsass.exe handles authentication.
  6. Userinit and Explorer start, and at this point the per-user autostart locations run.
Why the examiner cares about step 3

Drivers marked boot-start load before most security software. A rootkit that installs itself as a boot-start driver is running before anything that might detect it. That is why persistence entries are examined from a mounted image offline, not by running a tool on the live suspect machine, where the rootkit controls what the tool is allowed to see.

6.2

Startup in Windows NT and later — the six steps

Although Windows NT differs greatly from Windows 95 and 98, the startup method for NT, 2000 and XP is essentially the same. Any computer using NTFS performs these six steps when it is turned on:

  1. Power-on self test (POST)
  2. Initial startup
  3. Boot loader
  4. Hardware detection and configuration
  5. Kernel loading
  6. User logon

The files used to start Windows can be located on the system partition or the boot partition.

The Vista change. When Microsoft developed Vista it updated the boot process to use the Extensible Firmware Interface (EFI) as well as the older BIOS system — EFI boot firmware is designed to provide better protection against malware than BIOS does. The single Ntldr program used by Windows XP was replaced by three boot utilities:

UtilityRole
Bootmgr.exeThe Windows Boot Manager — controls boot flow and allows booting multiple operating systems.
Winload.exeThe OS loader — installs the kernel and the Hardware Abstraction Layer (HAL), and loads memory with the necessary boot drivers.
Winresume.exeRestarts the system after it goes into hibernation mode.
6.3

Startup in Windows 7, 8 and 10 — the BCD store

Since Vista, the boot process uses a boot configuration data (BCD) store. For BIOS-designed desktops and laptops, a BCD Registry file in the \Boot\Bcd folder is maintained to control the boot process. In Windows 8 and 10 the BCD contains the boot loader that initiates the system's bootstrap process.

The BCD is a Registry file you cannot open with Regedit

To access the BCD you use the BCD Editor — Regedit and Regedt32 are not associated with this file. This catches people out: the BCD is a Registry hive in format, but it is deliberately outside the normal Registry tooling. For an examiner this is useful, because a change to the boot configuration will not show up in an ordinary Registry review.

Keys at boot time: press F8 or F12 during the bootstrap process to reach the Advanced Boot Options menu, which offers Safe Mode, Enable boot logging and Disable Driver Signature Enforcement. Press F2 or Delete to reach the firmware and modify the boot priority order — which is what you change to boot your own forensic media.

Virtual Machines

Virtual machines enable you to run another operating system on an existing physical computer — known as the host computer — by emulating a computer's hardware environment. More companies turn to virtualization to reduce hardware cost, so the number of investigations involving virtual machines keeps increasing.

8.1

The two roles, and why both are examinable

Virtual machines let you run another OS on an existing physical computer — the host — by emulating a computer's hardware environment. The textbook gives three reasons an investigator meets them. First, new versions of operating systems and applications are released constantly while older versions remain in use, and you will face the challenge of having enough resources to support the variety of software you encounter — a virtual server lets you view legacy systems. Second, more companies are turning to virtualisation to reduce hardware costs, so the number of investigations involving virtual machines will keep increasing. Third, a VM lets you emulate actions taken by a suspect, or by malware.

The VM as evidence

A suspect runs their activity inside a virtual machine so the host looks clean. The entire VM is a handful of files on the host disk — and those files are a complete computer waiting to be examined.

The VM as laboratory

You mount a suspect image, or run a suspicious executable, inside an isolated VM. If it is malicious it destroys a virtual machine you can discard, not the laboratory workstation.

The two main files, whatever the product

A virtual machine typically consists of several files, but two matter most. The configuration file holds the hardware settings — RAM, network configuration, port settings. The virtual hard disk file contains the boot loader program, the OS files and the user's data files. Depending on the virtualisation software these files may be organised differently, which is why you read the configuration before assuming anything.

Working the other way, several forensics analysis tools can convert a forensic image to an ISO image or a virtual hard disk (VHD) file, which lets you run a suspect's system as a virtual machine and see what they saw.

Two practical reasons the book gives for an investigator to use one: you may need a virtual server to view legacy systems, because new versions of operating systems and applications are released frequently while older versions remain widely used; and you may need to emulate actions taken by a suspect, or by malware. Several forensic analysis tools can convert a forensic image into a bootable virtual machine for exactly this purpose.

The two main files of a virtual machine

A virtual machine typically consists of several files, but two are the main ones:

  • The configuration file — holds the hardware settings: RAM, network configuration, port settings and so on.
  • The virtual hard disk file — contains the boot loader program, the operating system files and the users' data files.

Depending on the virtualization software these files may be organised differently, but the division is always the same: settings in one, the entire computer in the other.

This is how the Unit II golden rule is honoured today

Unit II insists: never analyse an artifact on the compromised system, and use a clean isolated host. A virtual machine with networking disabled and a snapshot taken beforehand is that clean isolated host, and it can be restored to its pristine state in seconds afterwards. The rule has not changed; the way it is implemented has.

The two gifts a VM gives the examiner

1. Free memory forensics. A running or suspended VM writes its RAM to a .vmem file on the host. That is a memory image obtained without any live capture at all — encryption keys, running processes and network connections included, ready for Volatility.

2. Free time travel. Every snapshot is a preserved earlier state of the machine. A suspect who "cleaned up" after an incident may have left a snapshot taken before the cleanup, and restoring it shows the machine as it was.

8.3

Creating a virtual machine

The common applications for creating virtual machines are VMware Server, VMware Player and VMware Workstation, Oracle VM VirtualBox, Microsoft Virtual PC and Microsoft Hyper-V, available in current versions of Windows Server. VirtualBox is open source, which makes it the realistic choice for a college laboratory.

The wizard sequence, as the textbook walks it:

  1. Start the Create Virtual Machine wizard — click New in the VirtualBox Manager.
  2. Name and operating system — give the machine a name, then set Type (for example Microsoft Windows) and Version (for example Windows 7 32-bit).
  3. Memory size — adjust the allocated memory to about 50% of your workstation's total RAM.
  4. Hard drive — choose Create a virtual drive now.
  5. Hard drive file type — select the format, such as VHD (Virtual Hard Disk).
  6. Storage and size — choose dynamically allocated or fixed size, then create.
  7. Install the guest operating system from an ISO or installation disc, exactly as on physical hardware.
Set these before you use it as a laboratory

Before running anything hostile inside it: take a snapshot of the clean state, disable networking, and disable shared folders. The snapshot is what lets you return the machine to a pristine condition in seconds; the other two are what keep whatever you run from reaching your host or the network.

8.4

Procedure — examining a VM found on a suspect machine

  1. Image the host first, in the normal way with a write-blocker, and hash it. The VM files are simply files within that image.
  2. Identify the virtualisation software from the installed-programs registry key and from the file extensions present.
  3. Extract the VM files from the image — disk, memory, snapshots, configuration and logs — and hash each one separately.
  4. Read the .vmx configuration before anything else. It tells you the network mode and, importantly, whether shared folders linked the VM to the host — a path by which data moved between the two.
  5. Examine the virtual disk as a disk image. Autopsy and FTK read .vmdk, .vhdx and .vdi directly; there is no need to boot anything.
  6. Analyse the .vmem file with Volatility if one is present — it is a memory capture handed to you.
  7. Examine every snapshot, not merely the current state.
  8. If you must run the VM, work on a copy, disable networking first, and record that you did so and why. Running it changes it, and you will be asked about that.

Real example — the clean laptop with a dirty virtual machine

A seized laptop looks innocuous: standard applications, no unusual browser history, nothing in the Run keys. But it has VMware installed and a 60 GB .vmdk in the user's Documents folder. S.2

The errors that cost most marks

Conceptual errors
  • Saying deletion erases the data
  • Claiming deleted data is always recoverable — wear-levelling and the garbage collector may have erased it
  • Confusing sectors with clusters
  • Expecting a small deleted NTFS file to appear in unallocated space
  • Saying resident files are ~700 bytes — the threshold is about 512
  • Confusing a hive with an HKEY
  • Treating displayed timestamps as reliable without checking $FILE_NAME
  • Forgetting that ADS is lost the moment the file is copied to FAT32
Procedural errors
  • Powering off a machine with an unlocked encrypted volume
  • Examining the registry on the live suspect machine
  • Collecting hive files but not their .LOG files
  • Interpreting timestamps before reading the time-zone key
  • Examining only the current VM state and ignoring the snapshots
  • Running a suspect VM with networking still connected
  • Trying to open the BCD store in Regedit instead of the BCD Editor
  • Keyword-searching in ASCII only on a Unicode file system
  • Trying to open the BCD store in Regedit instead of the BCD Editor
  • Leaving a solid-state device uncopied while the garbage collector runs
