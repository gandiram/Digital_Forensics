Part A · Chapter 9

Digital Forensics Analysis and Validation

You have an image of the suspect drive. Part A is what happens next: deciding how much of it to examine, proving mathematically that it has not changed, finding what the suspect deliberately hid, and reaching a machine you cannot physically visit.

01Nelson et al., Ch. 9 · pp. 378–381

Determining What Data to Collect and Analyze

What you examine depends on the nature of the investigation and the amount of data to process. Criminal investigations are limited to finding data defined in the search warrant. Civil investigations are limited by court orders for discovery. Private-sector investigations might examine only specific items, such as email. Narrowing the target simplifies and speeds up processing enormously.

Scope creep — the thing that ruins schedules

In the private sector, especially where litigation is involved or anticipated, the company attorney often directs you to recover as much information as possible. That becomes a major undertaking with many hours of tedious work, and it invites scope creep: the investigation expands beyond its original description because of unexpected evidence you find, prompting the attorney to ask you to examine other areas.

Why scope creep is getting worse

Defence attorneys typically have the right of full discovery of digital evidence used against their clients. New evidence can surface while complying with that request — and the defence is under no obligation to hand it back to the prosecution; they use it to defend the accused. So prosecution teams must now analyse evidence exhaustively before trial. Always document any request for additional investigation, so you can explain later why the case took longer than planned.

The ten standard steps for any investigation

  1. Wipe and prepare the target drive. IACIS recommends recently wiped media, reformatted and inspected for viruses. Tools: X-Ways Security, Digital Intelligence PDWipe, WhiteCanyon SecureClean. Some commercial tools wipe only up to 2 TB; the Linux zero method has no limit — sudo dd if=/dev/zero of=/dev/sdb. Check the of= device twice.
  2. Inventory the hardware on the suspect's computer and note its condition when seized.
  3. Check CMOS date and time. For static acquisitions, remove the original drive if practical, then read the system clock values.
  4. Record how you acquired the data — that you created a bit-stream image, and which tool. The tool should also produce an MD5 or SHA-1 hash for validating the image.
  5. Process methodically and logically when examining the image.
  6. List all folders and files. Autopsy and similar tools export the full listing to Excel or HTML. Note where each item of evidence was found and how it relates to the investigation.
  7. Examine the contents of all data files from the root directory down — except where a warrant or discovery demand defines a narrower scope, in which case look only for the listed items.
  8. Recover password-protected files that might be relevant, using OSForensics, AccessData PRTK, or Passware Kit Forensic.
  9. Identify every executable that does not match a known hash value. Note system files that are out of place, such as anything odd in System32.
  10. Maintain control of all evidence and findings, documenting everything as you go.

Known File Filter — eliminating the noise

Most files on any drive are operating-system and application files that have nothing to do with the case. Autopsy carries an indexed copy of the NIST National Software Reference Library (NSRL) of MD5 hashes, which lets you filter every known-good file out of view and concentrate on what remains. You can also build a known-bad hash set from files you have already identified, so the same contraband is flagged instantly on the next drive you examine.

Worked example · the employee running a side business

An employee is accused of running an online business on company time. You use the working hours as a time filter, and because the allegation is unauthorised Internet use you focus on temporary Internet files, Internet history and email. That narrow plan saves days. Then, while reading the emails, you find references to spreadsheets holding the business's financial figures — so you deliberately widen the plan to include those file types. Start with a plan, stay flexible, and revise it on purpose rather than searching haphazardly.

In practice today

The filtering idea has not changed but the volume has. A single modern endpoint can hold a terabyte, so examiners increasingly run targeted triage collection first — pulling only the artefacts that answer the question (browser history, event logs, $MFT, prefetch, registry hives) — and only image the full disk if triage justifies it. Tools such as Velociraptor and KAPE exist for exactly this. NSRL is still published by NIST and still the standard known-good reference set.

Validating Forensic Data

Validating digital evidence is one of the most critical aspects of the whole discipline, because ensuring the integrity of what you collect is what makes it presentable in court. Most forensics tools can hash an image file. Tools have limits, though, so advanced hexadecimal editors are needed for finer work.

What a hex editor gives you that a forensics suite does not

A full-featured hex editor can hash specific files or individual sectors rather than whole images. That matters when you are hunting a particular known file — say a known contraband image. Two files with exactly the same content have the same hash value even if the names are different, so with the hash in hand you can search for a file that has been renamed to look innocuous.

Block-wise hashing — finding a fragment, not a file

Hashing a whole file only helps if the whole file survives. Block-wise hashing hashes each sector or block separately, so if a suspect deleted a contraband image and only three of its clusters survive in unallocated space, those three clusters still match their known block hashes. Whole-file hashing would find nothing at all.

Worked example · the renamed file

A suspect renames evidence.jpg to winsock32.dll and drops it in a system folder. A filename search finds nothing. A hash search against the known-bad set matches instantly, because renaming a file changes not one bit of its content. This is why hashes, not names, are the identity of a file in forensics.

In practice today

The book's examples use MD5 and SHA-1. Both are now cryptographically broken for collision resistance — deliberate collisions have been demonstrated — so current practice is to record SHA-256, usually alongside MD5 for backwards compatibility with older case records. They remain acceptable for integrity checking of evidence, because an accidental collision is still vanishingly unlikely, but no new system should rely on them alone. India's Section 63 BSA certificate now expects the hash value of the record to be stated on the certificate itself.

Addressing Data-Hiding Techniques

Data hiding involves changing or manipulating a file to conceal information. The techniques are: hiding entire partitions, changing file extensions, setting the hidden attribute, marking clusters bad, bit-shifting, steganography, encryption and password protection.

1 · Hiding files using the operating system

The simplest trick is changing the file extension — an incriminating .xlsx renamed to .jpg. Open it in Excel and you get an error. But advanced forensics tools check file headers and compare them to the extension; a mismatch is flagged as an altered file needing more analysis. The other basic technique is the Hidden attribute in a file's Properties dialog, which any forensics tool sees straight through.

2 · Hiding partitions

Using diskpart remove letter at a PowerShell prompt unassigns a partition's drive letter, which hides it from File Explorer. diskpart assign letter puts it back. To detect this, account for all disk space on the evidence drive and analyse anything you cannot account for. Normal gaps between partitions are around 128 bytes in Windows Vista and later — anything much larger deserves a look.

How the tools show it. In WinHex a hidden partition appears with no drive letter against it, and the tool labels the boot partition “Start sectors” and the unallocated area “Unpartitionable space”. In Autopsy the same partition appears under Data Sources as a numbered volume — but only when you are viewing a forensic disk image, not when viewing in live mode.

3 · Marking clusters bad

An older FAT technique: using a disk editor such as Norton DiskEdit you type the letter B in the FAT entry for a good cluster, and the OS then treats it as unusable. Data can still be written and read there with a disk editor, but it is invisible to the operating system. Two things matter for the exam: if that FAT partition is later converted to NTFS the bad markings survive, and most GUI tools skip clusters marked bad — which is precisely why they may hold evidence.

4 · Bit-shifting

Bit-shifting changes data from readable code into something that looks like binary executable code, by rearranging the bits of each byte. Shift left to scramble, shift right to restore. Some malware uses this to hide its payload from antivirus hashing; malware attacking Office files sometimes embeds executable code at the end of a document, bit-shifted, and reverses the shift at runtime.

5 · Steganography and steganalysis

Steganography is hiding a message so that only the intended recipient knows it is there. Detecting and analysing it is steganalysis. A useful tell: two images that look identical and may even have the same file size will have different hash values if one carries an invisible watermark or payload. Johnson and Jajodia named five steganalysis attacks — which one you can use depends entirely on what you happen to have.

6 · Encryption and password recovery

Encrypted files are encoded to prevent unauthorised access; without the passphrase, recovery is difficult. Key sizes from 128 to 4096 bits make brute force effectively impossible with current technology. Some commercial encryption uses key escrow — designed so users can recover data after forgetting a passphrase, and usable by examiners for the same purpose. The textbook's blunt advice still holds: if you encounter encrypted data, make an effort to persuade the suspect to reveal the passphrase.

Method 1
Dictionary attack

Tries common words from a dictionary. Most crackers ship dictionaries in many languages, and you can import unique words extracted from the evidence itself.

Method 2
Brute-force attack

Every possible letter, number and character. Eventually cracks any password, but needs enormous time and processing power as length grows.

Method 3
Rainbow table

A file of precomputed hash values for every possible password. No conversion needed at run time, so it is much faster than the other two.

The counter-measure: salting

A hybrid attack builds a profile of the suspect — relatives' names, pets, favourite colours, schools — because people reuse what they are comfortable with. Against rainbow tables, the defence is salting: extra bits are added to the password before hashing, which alters the hash value and makes precomputed tables useless. Named tools in the text: Last Bit, AccessData PRTK, ophcrack, John the Ripper, Passware.

In practice today

Full-disk encryption has changed the balance. BitLocker, FileVault and LUKS are on by default on much modern hardware, and a powered-down encrypted laptop is often simply unreadable. This is the single strongest argument for live acquisition (Topic 6): while the machine is running, the decryption key is in RAM and the volume is mounted in the clear. Pull the plug and you may lose the case. Practically, examiners now hunt for the recovery key in cloud accounts, in enterprise key escrow (Active Directory, Intune, MDM) or in a RAM capture — not in a brute-force run.

Performing Remote Acquisitions

Remote acquisition means connecting to a suspect computer over a network and copying data from it — the whole disk, or sparse or logical fragments. It saves the travel, and it minimises the chance the suspect notices an investigation is under way. Almost all remote acquisitions are live acquisitions rather than static ones.

Why it appeals
  • No travel to the suspect's location
  • Far less chance of tipping off the suspect
  • Some tools push an agent through an encrypted link with no manual step at the far end
  • Volatile state can be captured that a static acquisition would lose
What gets in the way
  • Antivirus, antispyware and firewall tools may block or alert on the agent
  • If suspects have administrator rights they can install their own security tools that alarm on remote access
  • Advanced privileges are required to push agent applications at all
  • Data transfer speed and network access permissions

How the connection is built

EXAMINERForensic workstationRuns the console — ProDiscover IR, EnCase Endpoint Investigator, F-Response
LINKEncrypted channel256-bit AES or Twofish, GUID-tagged packets, password protected
SUSPECTRemote agente.g. PDServer — must be installed on the suspect machine first

Three ways to get the agent onto the target. The textbook uses ProDiscover's PDServer as its worked example:

  1. Trusted CD. A special CD, DVD or USB containing the agent, loaded manually on the suspect computer.
  2. Preinstallation. The agent is baked into the standard OS build for high-risk machines, so security staff can respond to attacks quickly. Management tools such as DameWare or Hyena then initiate the connection.
  3. Pushing out and running remotely. The agent is downloaded to the remote computer on demand, and data is collected in real time.
The five security features that make it evidentially sound

Password protection — the agent is password-protected and the password is encrypted at all times. Encryption — 256-bit AES or Twofish on all traffic. Secure protocol — every connection carries globally unique identifiers (GUIDs) so packets cannot be inserted into the stream. Write-protected trusted binaries — the agent can run from read-only media. Digital signatures — the agent and its driver are signed, proving they were not tampered with before or during the connection.

The agent can also run in stealth mode; Task Manager would otherwise list the process by name, so the process name can be changed to look like an OS function.

What a remote tool can do besides imaging

  • Capture volatile system state information
  • Analyse currently running processes on the remote system
  • Locate unseen files and processes that might be malware or spyware
  • Remotely view and listen to IP ports on a compromised system
  • Run hash comparisons on the remote system to search for known Trojans and rootkits
  • Create a hash inventory of all files remotely — a baseline to compare against if the machine is later attacked
In practice today

This is now the mainstream way large organisations do forensics, not the exception. Velociraptor (open source, acquired by Rapid7 in 2025) can collect targeted artefacts and even memory across thousands of endpoints at once using its own query language, VQL. F-Response remains the vendor-neutral way to expose a remote disk read-only to any tool you like. Commercial EDR platforms increasingly ship the same capability. The forensic principles are unchanged — you still need authorisation, an audit trail, and a hash of everything you pull — but “go to the machine” is no longer the default.

Part B · Chapter 10

Network Forensics

Disk forensics asks what is on this machine. Network forensics asks how the attacker got there, what moved across the wire, and whether they are still inside. The evidence is transient, often never written to permanent storage, and the trail goes cold fast.

05Nelson et al., Ch. 10 · pp. 435–437

Network Forensics Overview

Network forensics is the process of collecting and analysing raw network data and tracking network traffic systematically, to ascertain how an attack was carried out or how an event occurred on a network.

The core idea: know what normal looks like

When intruders break into a network they leave a trail, and spotting variations in traffic is how you find it — so knowing your network's typical patterns is essential. If a company's peak use is normally between 6 a.m. and 6 p.m., that is when spikes belong. A usage spike in the middle of the night is unusual activity and the administrator should investigate it. Network forensics also tells you whether you are really under attack, or whether someone installed an untested patch or a buggy custom program. A lot of time gets wasted proving that an “attack” was a bug.

Hardening comes before forensics

Network forensics determines how a breach happened, but steps must be taken to harden the network before one does. Hardening ranges from applying the latest patches to adopting a layered network defence strategy — layers of protection that hide the most valuable data at the innermost part of the network, so the deeper an attacker gets, the harder access becomes.

Defense in Depth — the NSA's three modes

The NSA's defense in depth (DiD) strategy has three modes of protection. If one mode fails, the others can still thwart the attack.

Mode 1
People

Hire well-qualified people and treat them well, so they have no reason to seek revenge. Train them adequately in security procedures and make sure they know the security policy. Physical and personnel security sit here.

Mode 2
Technology

A strong network architecture and tested tools — intrusion detection systems, firewalls. Regular penetration testing with risk assessment. Also the systems that allow quick, thorough analysis when a breach does occur.

Mode 3
Operations

Day-to-day work: updating security patches, antivirus and operating systems, plus assessment and monitoring procedures and disaster recovery plans.

Where the threat actually comes from

In the early-to-mid 1990s roughly 70% of network attacks came from employees. That was then compounded by contract staff, who often hold the same network privileges as full-time employees. Increasing Internet use has since raised external threats sharply, so the split is now about 50-50. Small companies of fewer than ten employees often think internal precautions are unnecessary, which makes them more vulnerable to staff passing proprietary information to competitors.

In practice today

Two things have shifted. First, encryption is now the default: the vast majority of web traffic is TLS, so payload inspection is often impossible and modern network forensics leans heavily on metadata — who talked to whom, when, how much, over which protocol. Second, the perimeter has dissolved; with cloud and remote work, the equivalent evidence increasingly lives in VPC/NSG flow logs, CloudTrail and identity-provider sign-in logs rather than a span port in a server room. The analytical logic — baseline, then look for deviation — is unchanged.

Performing Live Acquisitions

Live acquisitions are especially useful with active network intrusions and attacks, or where you suspect employees are accessing areas they should not. They are increasingly a necessity, because attacks may leave footprints only in running processes or RAM — some malware disappears entirely once the system restarts.

The uncomfortable trade-off you must state in an exam answer

After a live acquisition, information on the system has changed, because your actions affect RAM and running processes. Which means the result cannot be reproduced. Live acquisitions therefore do not follow typical forensics procedures — and that is exactly why documenting every action and its reason is critical.

The order of volatility governs everything

The order of volatility (OOV) determines how long a piece of information lasts on a system. RAM and running processes might exist for milliseconds; files on the hard drive might last for years. You always collect the most volatile first.

The six-step live acquisition procedure

  1. Prepare and test your boot media. Create or download a bootable forensic CD or USB drive and test it before using it on a suspect drive. If the suspect system is on your network and reachable remotely, add the network forensics tools to your workstation instead.
  2. Start the log. Keep a log of all your actions. Documenting your actions and the reasons for them is critical.
  3. Set up somewhere to put the data. A network drive is ideal. If none is available, connect an external drive to the suspect system — and note that step in your log.
  4. Copy the physical memory. This is the step that justifies the whole exercise. Tools: WindowsScope, Magnet AXIOM, OSForensics, FTK Imager, Belkasoft RAM Capturer, Mandiant Memoryze.
  5. Vary by incident. For an intrusion you might check for a rootkit, access the firmware to see whether it has changed, image the drive over the network, or shut down and make a static acquisition later.
  6. Hash everything you recovered during the live acquisition, so it cannot be altered later without detection.
Worked example · why step 4 comes before step 5

A workstation is beaconing to an unknown IP. The responder captures RAM first. That capture contains the injected process (which has no file on disk), the decryption key for the malware's configuration, and the live socket to the command-and-control server. Only then is the disk imaged. Had the machine been powered off first — the instinctive “safe” move — all three would have been gone, and the disk image alone would have shown almost nothing.

GUI tools versus command line

GUI tools are easy to use but often demand a lot of system resources, and some can give false readings on Windows. Command-line tools generally give you more control — which is why the textbook recommends becoming familiar with Sleuth Kit and similar. Kali Linux carries over 300 tools including password crackers, network sniffers and freeware forensics utilities.

In practice today

Memory forensics has become routine rather than specialist. Volatility 3 is the standard analysis framework and no longer needs exact OS profiles, so it works against current Windows builds. For capture, Magnet RAM Capture, DumpIt, Belkasoft RAM Capturer and LiME (Linux kernel module) are the common free choices. In cloud environments you generally cannot attach a tool to hypervisor memory — you either pre-install an agent or use the provider's run-command facility, which is a decision that has to be made before the incident, not during it.

Developing Standard Procedures for Network Forensics

Network administrators want to find compromised machines, get them offline and restore them as fast as possible to minimise downtime. Taking the time to follow standard procedures is what ensures all compromised systems have been found, and that the attack method is understood well enough to prevent a repeat.

Procedures must be based on the organisation's needs and should complement its network infrastructure. Administrators need to learn how to stop intruders and determine how they got in, what they copied, altered or deleted, and whether they are still on the network.

The five-step standard procedure

  1. Always use a standard installation image for systems on the network. This is not a bit-stream image — it is an image containing all the standard applications in use. Keep MD5 and SHA-1 hash values of every application and OS file.
  2. Fix the vulnerability first. When an intrusion happens, make sure the hole has been closed so other attackers cannot use the same opening while you investigate.
  3. Retrieve all volatile data — RAM and running processes — by doing a live acquisition before turning the system off.
  4. Acquire the compromised drive and make a forensic image of it.
  5. Compare against the standard image. Compare hash values of common files such as system executables and standard DLLs, and establish which have changed.
The step that makes the other four work

Step 1 is done before any incident. Without a known-good baseline image and its hashes, step 5 is impossible — you would have no way of telling a trojaned svchost.exe from the real one. Every organisation that skips step 1 discovers the cost of it during its first real intrusion.

A difference from disk forensics worth stating

In disk forensics you work from the image to find deleted or hidden files. In network forensics you often have to restore the image to a physical drive and run it, because the only way to understand how the attacker's malware behaves is to watch it work. Intruders might have transmitted a Trojan that gives them access and then installed a rootkit — a collection of tools performing network reconnaissance, keylogging and similar.

The standards landscape the textbook points at is still the right one: NIST SP 800-86, “Guide to Integrating Forensic Techniques into Incident Response” remains the reference document for building these procedures, alongside published frameworks from military, law-enforcement and industry perspectives.

In practice today

Two additions to the five steps. First, most organisations now run continuous collection rather than post-incident collection — Zeek logs, EDR telemetry and flow records are already being written before anything happens, so step 3 partly answers itself. Second, breach-notification law now imposes clocks on the procedure: GDPR gives 72 hours from awareness to notify the supervisory authority, and India's CERT-In directions require reporting of specified cyber incidents within 6 hours. Your procedure has to fit inside those windows.

Using Network Tools

Network logs record traffic in and out of a network — servers, routers, firewalls and other devices record the activities and events that move through them. The tools that read those records are the working instruments of network forensics.

Reading a tcpdump line

A common way to examine traffic is the tcpdump command-line program, which can produce thousands of lines of records. Every line follows the same format.

Fri Dec 15 15:06:33 2017; TCP; eth0; 1296 bytes; from 204.146.114.10:1916 to 156.26.62.201:126
timewhen it happened protocolTCP interfaceEthernet 0 size1296 bytes source → destinationthe number after the colon is the port
What to look for in the port numbers

Port information gives you clues. A particular IP address arriving frequently on an unusual port is worth investigating, and a receiving port above 1024 should raise a flag. Check assigned port numbers against the Internet Assigned Numbers Authority (IANA) list. Aggregating the logs — top ten external sites visited, top ten internal users by bytes — reveals patterns such as an employee transmitting data to one particular address again and again.

Packet analyzers

Packet analyzers are devices or software placed on a network to monitor traffic. Most administrators use them for security and for tracking bottlenecks — but attackers use them to get information covertly. Most work at Layer 2 or 3 of the OSI model; understanding what is really happening often means looking at higher layers using the custom software that comes with switches and routers.

Nearly everything reads the Pcap (packet capture) format — Libpcap on Linux, Winpcap on Windows. Because of that shared format, many investigators capture with tcpdump and then analyse in Wireshark, taking the strengths of each.

The warning attached to all of them

These tools are equally useful to an attacker who obtains administrative rights. The textbook's own classroom example: one student logged on to another student's server and shut it down remotely, because no password had been set for the default account. And when your investigation turns up other companies that have been compromised, do not make that public — contact them and enlist their help tracking the intruder.

In practice today

Wireshark and tcpdump remain the standard for single-host analysis, but at enterprise scale the stack has moved on. Zeek (formerly Bro) produces structured protocol logs — HTTP, DNS, SSL, files — rather than raw packets, and is what most detection pipelines actually consume. Arkime (formerly Moloch) does indexed full-packet capture with a searchable web interface. Security Onion bundles both with dashboards. The practical constraint is storage: at 1 Gbps sustained, full capture generates roughly 450 GB per hour, so most organisations keep Zeek metadata long-term and full packets only for a short rolling window.

Examining the Honeynet Project

The Honeynet Project was developed to make information widely available in an attempt to thwart Internet and network attackers. Many people participate in this worldwide project, which is now a non-profit organisation.

Objective 1
Awareness

Make people and organisations aware that threats exist and that they might be targets.

Objective 2
Information

Provide information on how to protect against those threats — including how attackers operate, how they communicate, and what tactics they use.

Objective 3
Tools

For people who want to do their own research, offer the tools and the methods.

The two threats it was built to study

Distributed denial-of-service (DDoS)

Hundreds or even thousands of machines are used. These machines are called zombies, because they have unwittingly become part of the attack. A trace of a DDoS attack might run through other organisations' networks, not just yours or your ISP's. When the first DDoS attacks began, the main concerns were the high monetary impact and the time it took to track them down.

Zero day attacks

Attackers look for holes in networks and operating systems and exploit them before patches are available. Vendors usually are not aware the vulnerabilities exist, so no patch has been developed or released. Penetration testers try to break in to find undiscovered vulnerabilities and predict where the next wave of attacks will come from.

Honeypots and honeywalls

The project works by installing honeypots and honeywalls at different locations around the world.

ATTACKERInternetScans, finds the exposed service, connects
HONEYPOTThe decoy machineA computer set up to look like any other machine on your network. Its purpose is to lure attackers — it contains no information of real value. You can take it offline to analyse it without affecting the running of your network.
HONEYWALLThe watcherA computer set up to monitor what is happening to the honeypots on your network and record what attackers are doing.
The one-line distinction students get wrong

The honeypot is the bait. The honeywall is the camera. They are two different machines with two different jobs, and an exam answer that describes only the honeypot has answered half the question.

The value-versus-cost judgement

In any organisation you have to determine the value of the data you are protecting and weigh it against the price of the defence system you plan to install. When an attack strikes, your first response is to stop it and prevent it going further. Then you review which defence procedures worked and what additional ones are needed. Training and informing IT staff is critical.

In practice today

The Honeynet Project is still running as a non-profit and still publishes tools and research. The deployment model has moved to containers: T-Pot, maintained by Deutsche Telekom Security, bundles around twenty honeypots with Elastic dashboards and an attack map in a single Docker stack, and is what most universities now use for practical work. Cowrie is the standard SSH/Telnet honeypot, Dionaea the standard malware collector across SMB, HTTP, FTP and SIP. The newest research direction is LLM-backed honeypots that generate convincing shell responses on the fly, because static emulated shells are now easy to fingerprint. The defining property has not changed: a honeypot has no legitimate users, so any interaction with it is malicious by definition — which is why it produces almost no false positives.

Identifying Digital Evidence

Digital evidence is any information stored or transmitted in digital form. Because you cannot see or touch it directly, it is difficult to explain and describe — is it real, or merely a representation of real information? Courts have settled the question: digital evidence is accepted as physical evidence, meaning digital data is treated as a tangible object, like a weapon or a paper document.

The four general tasks

Task 1
Identify

Identify digital information or artefacts that can be used as evidence.

Task 2
Collect

Collect, preserve and document the evidence.

Task 3
Analyse

Analyse, identify and organise the evidence.

Task 4
Reproduce

Rebuild the evidence or repeat the situation to verify that the results can be reproduced reliably.

One team, or one procedure

Collecting digital devices must be done systematically. To minimise confusion, reduce the risk of losing evidence and avoid damaging it, only one team should collect and catalogue digital evidence at a scene or lab, if practical. Where there is too much evidence for one team, all examiners must follow the same established operating procedures and a lead or managing examiner must control collecting and cataloguing. Use standardised forms for tracking, so evidence is handled consistently.

The standards that make evidence portable between countries

Establishing recognised standards is a real challenge. Consider raids conducted simultaneously in many countries, or anti-cartel investigations running in several locations at once — hundreds of drives, phones and storage devices seized across multiple sites. If the organisations in those countries have agreed on proper procedures, the evidence can be presented in any jurisdiction confidently. The working rule is that the highest control standard should be applied to evidence collection in all jurisdictions.

  • ISO/IEC 27037 — guidance on identifying, collecting, acquiring and preserving digital evidence; the international reference for both criminal and civil procedure
  • SWGDE, the Scientific Working Group on Digital Evidence — sets standards for recovering, preserving and examining digital evidence
  • NIJ, “Electronic Crime Scene Investigation: A Guide for First Responders” — guidelines for those who protect an electronic crime scene and search for, collect and preserve evidence

Note the limits: laws in only about 40% of the world are based on English or Dutch common law, each country interprets what can be presented differently, and evidence collection is now further complicated by mobile devices and cloud storage becoming the norm.

In practice today — India

For Indian students this is the most important update in the unit. The Indian Evidence Act 1872 was replaced by the Bharatiya Sakshya Adhiniyam (BSA) 2023 with effect from 1 July 2024. The familiar Section 65B certificate is now Section 63. Two changes matter for practical work: the certificate must be signed by both the person in charge of the device and an expert, and it must state the hash value of the electronic record. Section 63 also broadens “computer” to “computer or any communication device”. Technically flawless imaging still fails in an Indian court without a properly executed Section 63 certificate.

Collecting Evidence in Private-Sector Incident Scenes

Investigating and controlling incident scenes in the private sector is much easier than at a crime scene. The scene is usually a workplace — a contained office or manufacturing area — where everything from the computers to the surrounding facility is under a controlled authority: company management.

The advantages you have
  • Businesses typically hold inventory databases of hardware and software, so you know what you are walking into
  • Knowing which applications are on the machine tells you which forensic tools you need and how to conduct the analysis
  • Knowing the company's standard browser lets you build standard examination procedures for downloaded data
  • With a policy in place you can conduct covert surveillance with little or no cause, and access company systems without a warrant — something law enforcement cannot do
The condition attached to all of it

If a company does not display a warning banner or publish a policy reserving the right to inspect digital assets, employees have an expectation of privacy, and that prevents the employer from legally conducting an intrusive investigation.

A well-defined policy should state that the employer has the right to examine, inspect or access any company-owned digital asset. As standard practice companies should use both a warning banner and a policy statement — if an incident escalates to a criminal complaint, prosecutors prefer showing juries a warning banner rather than a policy manual, because it leaves a much stronger impression.

When may you actually start?

Having a policy is not the same as having a reason. Organisations must also have a well-defined process describing when an investigation can be initiated. At a minimum, most policies require reasonable suspicion that a law or policy is being violated. Example: a policy forbids using company computers for outside business, and a supervisor notices a change in work behaviour suggesting an employee is doing exactly that. Generally that is enough to warrant an investigation.

What to do if you find evidence of an actual crime

  1. Determine whether it meets the elements of criminal law. You may have to consult your organisation's attorney to decide whether the situation is a potential crime at all.
  2. Inform management. They may have concerns you do not — particularly protecting confidential business data mixed in with the criminal evidence, known as commingled data.
  3. Protect the commingled data. Coordinate with management and the attorney. Once you submit evidence containing sensitive information to the police it becomes public record; there are exceptions for protecting sensitive company information, but ultimately a judge decides what is protected.
  4. Stop your investigation. This is the step people get wrong. Once you have discovered, documented and reported the crime, stop — so that you do not violate constitutional restrictions on obtaining evidence.
  5. Do not gather more on police instructions. If you keep collecting at the direction of the police without a warrant, you risk becoming an agent of law enforcement. The police and prosecutor should issue a subpoena for any new evidence, which minimises your exposure to civil liability.
  6. Keep all documentation of evidence collected during the internal policy investigation.
The one case where you must stop immediately

If child sexual abuse material is discovered, the company or its agents must notify law enforcement immediately. A private-sector investigator is not permitted to examine those files at all — the material is contraband and must not be stored by any person or organisation other than a law enforcement agency. Stop what you are doing and call the authorities.

ISPs are a special category. They may investigate computer abuse committed by their own employees but not by customers, and must preserve customer privacy, especially with email. They can, however, be called on to investigate customer activity that creates an emergency situation — defined as the immediate risk of death or personal injury, such as a bomb threat found in an email.

Processing Law Enforcement Crime Scenes

To process a crime scene correctly you must be familiar with the criminal rules of search and seizure. A law enforcement officer can search for and seize criminal evidence only with probable cause — the standard specifying whether an officer has the right to make an arrest, conduct a search, or obtain a warrant.

How specific must a warrant be?

Warrants may only be issued “particularly describing the place to be searched and the persons or things to be seized”. The courts read particularly strictly: a warrant can authorise a search only of a specific place for a specific thing.

Too general

“A house on Elm Avenue between Broadway and Main Street” — unless only one house fits that description. A weak warrant creates problems later during prosecution, and a judge can exclude everything obtained under it.

Specific enough

“123 Elm Avenue”. For the items, courts have allowed more general wording for digital evidence — you can say “computer and all associated parts” rather than naming an exact model.

Two terms you must know

Innocent information is unrelated material included with the evidence you are trying to recover — personal records of innocent people, or confidential business information. When you find commingled evidence, judges often issue a limiting phrase to the warrant, which allows police to separate innocent information from evidence. The warrant must list which items can be seized.

The plain view doctrine

Objects falling in the direct sight of an officer who has a right to be in a location are subject to seizure without a warrant and can be introduced into evidence. Three criteria must be met.

Criterion 1
Lawful presence

The officer is where he or she has a legal right to be.

Criterion 2
Unaided senses

Ordinary senses must not be enhanced by advanced technology — binoculars, for instance.

Criterion 3
By chance

Any discovery must be by chance. Police are not permitted to move objects to get a better view.

In Arizona v. Hicks (1987) the officer acted unlawfully because he moved stereo equipment, without probable cause, to record its serial numbers. The doctrine has since been expanded to plain feel, plain smell and plain hearing.

The Horton three-prong test (1990)

Horton v. California removed the requirement that discovery be inadvertent, because that term proved hard to define. The test now requires three things: the officer must be lawfully present where the evidence can be plainly viewed; the officer must have a lawful right of access to the object; and the incriminating character of the object must be immediately apparent.

Why plain view is being rejected for digital searches

A forensic examiner sees thousands of files while searching, so it is tempting to argue everything on the drive is in plain view. Courts increasingly disagree. Example: a warrant authorises searching a computer for drug-trafficking evidence; during the search the examiner opens an .avi file and finds child abuse material. At that point she must get an additional warrant or an expansion of the existing one before continuing. In United States v. Comprehensive Drug Testing (2010) a warrant covering ten baseball players led to 200 more being implicated during the examination — investigators argued plain view, and the court disagreed. A separate warrant was required.

Preparing for a Search

Preparing for search and seizure is probably the most important step in digital investigations. The better you prepare, the smoother the investigation. Information comes from the victim (the complainant) and an informant — who could be the detective assigned to the case, a law enforcement witness, or a manager or co-worker of the person of interest.

The seven preparation tasks

  1. Identify the nature of the case. Private or public sector? A private case might be Internet abuse or an EEO or harassment complaint; a law enforcement case could be anything from check fraud to homicide. The nature dictates how you proceed and what resources you need.
  2. Identify the type of OS or digital device. Estimate storage size and how many devices you must process. Windows, Linux, macOS, iOS, Android; PCs, smartphones, tablets, laptops, wearables. Private-sector investigators have configuration management databases to consult; law enforcement often does not, because the scene is not controlled.
  3. Determine whether you can seize the devices. Law enforcement needs a warrant to remove computers. If removing them would irreparably harm a business, they should not be taken offsite unless you have disclosed that effect to the judge. Also consider files stored offsite and accessed remotely, and cloud storage — which essentially cannot be located physically.
  4. Get a detailed description of the location. Environmental and safety issues are the main concern. Identify potential hazards before you arrive.
  5. Determine who is in charge. Private-sector investigations usually need only one responder. Law enforcement often needs additional staff, and large-scale investigations need a designated crime or incident scene leader whom everyone cooperates with.
  6. Decide whether you need additional technical expertise. A data centre with RAID arrays and high-end Linux servers may need a server specialist; an Oracle installation may need a database specialist; mobile devices need someone who can handle them. If you recruit a non-investigator, train them in investigative technique — an untrained specialist can destroy evidence unintentionally no matter how carefully you brief them.
  7. Determine the tools you need. Being overprepared is better than being underprepared, particularly when you cannot take the machine back to the lab.
Hazardous scenes — the part of task 4 that gets its own procedure

Some scenes involve a methamphetamine lab or biological, chemical or nuclear contaminants. There you rely on a HAZMAT team. If decontamination would destroy the electronic evidence, a HAZMAT specialist or an investigator in HAZMAT gear must image the drive — and if you have to coach the specialist, be exact and articulate, because ambiguous instructions destroy evidence.

Practical technique: put the target drive in a HAZMAT bag with the data and power cables led out through an airtight seal, so contaminants cannot reach the drive. Acquire, power down, disconnect, then let the technician decontaminate the bag. Above 80 °F take measures against overheating — sealed ice packs or double-wrapped bags of ice, so no moisture leaks onto the drive. In extreme cases you may have to sacrifice cables entirely, or accept that contamination makes acquisition impossible.

The two field kits

Initial-response field kit

Lightweight and easy to transport — arrive, acquire, return to the lab quickly.

  • Small computer toolkit; JIS and ANSI screwdriver sets
  • Large-capacity target drive; USB drives or a portable hard drive
  • Two antistatic wrist bands; ten antistatic computer evidence bags
  • IDE ribbon and SATA cables; laptop 40-to-44-pin adapter
  • Forensic boot media containing an acquisition utility
  • FireWire or USB dual write-protect external bay
  • Laptop or tablet; flashlight
  • Digital camera with spare batteries
  • Ten evidence log forms; twenty evidence labels, tape and tags
  • Notebook or digital dictation recorder; permanent ink marker
Extensive-response field kit

Everything you can afford to take. On arrival you extract only what you need, which protects the equipment and reduces how much you must track at the scene.

  • The complete initial-response field kit
  • Assorted technical manuals, from OS references to forensic analysis guides
  • Laptop or tablet with cables and connectors
  • Two electrical power strips
  • Additional hand tools — bolt cutters, pry bar, hacksaw
  • Leather gloves and disposable latex gloves in assorted sizes
  • External USB drives

Securing a Computer Incident or Crime Scene

The goal of securing a scene is to preserve the evidence and keep information confidential. The guiding rule is to define a perimeter wider than you think you need, because you can always shrink it later — you cannot re-secure ground people have already walked over.

What to do
  • Use whatever is practical — barrier tape, closed doors, a posted officer — so only authorised people can enter
  • Remove anyone who is not investigating, unless you need their help (the network administrator may be needed to recover data)
  • Let nothing in the area move until you have recorded it
  • Be professional and courteous to onlookers, but give out no information; refer journalists to a public information officer
  • Legal authority differs: law enforcement secures the scene under a warrant, corporate investigators under company authority
Professional curiosity — the commonest way evidence dies

Evidence is routinely lost or corrupted because of professional curiosity: the presence of police officers and other professionals who are not part of the processing team, but have a compelling interest in seeing what happened. Their presence can contaminate the scene directly or indirectly.

Even people authorised and trained to search crime scenes alter evidence inadvertently. Starting a computer without forensic boot media changes date and last-access timestamps immediately.

The story the textbook tells to make the point stick

A lead detective recovered a good latent fingerprint from a homicide scene. It matched neither the victim nor anyone who knew her, so he kept it on file for years, convinced it belonged to the murderer. When his department bought an Automated Fingerprint Identification System, he asked the acceptance-testing team to run it. Within minutes AFIS found a near-perfect match — the print was his own.

Fingerprints have an escape route from this: elimination prints can be taken from everyone with access to the scene. Digital evidence has no equivalent elimination process. There is no way to subtract your own contamination afterwards, which is why nobody may examine a suspect's computer before you have captured and preserved an image.

15Nelson et al., Ch. 4 · pp. 167–172

Seizing Digital Evidence at the Scene

With proper search warrants, law enforcement can seize all digital systems and peripherals. In private-sector investigations you might have only the authority to make an image of the suspect's drive — investigators there rarely have authority to seize everything.

Three questions to ask before you collect anything

  • Do you need the entire computer and all peripherals and media in the immediate area — and how will you protect them in transport, including blocking devices from reaching wireless networks on the way?
  • Is the computer powered on when you arrive?
  • Is the suspect in the immediate area? Could they damage or destroy the machine? Will you have to separate them from it?

For a criminal case involving, say, a drug dealer's computer, you take the entire machine plus every peripheral and item of media in the area — smartphones, USB devices, discs, printers, cameras, scanners, and increasingly smart TVs, gaming systems and other network-attached devices. For employee misconduct you may need only a few specific items.

Recording the scene, in order

  1. Keep a journal. Date and time you arrived, the people you encounter, and notes on every important task. Update it as you go.
  2. Video and still recordings. Start with the overall scene, then close-ups — including the back of every computer. Label every cable with a number or letter before recording the back, so the configuration can be rebuilt at the lab. Record the floor, the ceiling, all access points such as doors and windows, and look under tables and desk drawers for anything taped out of sight. Remove false ceiling tiles and record that space too. Pan slowly to avoid blurring, and keep a camera log.
  3. Sketch the scene. A rough draft with dimensions and distances between fixed objects — “the suspect's computer is on the south wall, three metres from the southeast corner”. Redraw it cleanly, preferably in drawing software, for the report.
  4. Check the state of every device as soon as possible, because digital data is volatile. On, off, hibernating or asleep?

The decision everything turns on

Is the computer powered on?
▼
If it is OFF Leave it off. There is nothing to gain and everything to lose by powering it on. Photograph, label, bag and tag.
If it is ON Use professional judgement. Standard practice used to be to kill the power, and that is still generally acceptable on older Windows and MS-DOS systems, where cutting power usually preserves data. On most modern Windows, UNIX and Linux computers you should generally do an orderly shutdown first — but every shutdown carries risk, so you or your supervisor may have to decide the best procedure.
Why the rule changed — and why it is a judgement call

More investigations now revolve around network and Internet cases which rely heavily on log file data. Certain files, such as the Windows Event log and Security log, can lose essential network activity records if power is terminated without a proper shutdown. Some government agencies still teach investigators to “pull the plug”. Ultimately it is the Digital Evidence First Responder's call.

There are also self-destruct mechanisms to consider. A classic trick altered the DOS command.com so that typing dir actually ran deltree, wiping every folder. More advanced versions overwrite the drive, and some owners set the machine to erase itself if the wrong screensaver password is entered.

If it is on and you are staying live

  • Save data in current applications as safely as possible, and record all active windows or shell sessions
  • Do not examine folders or network connections or press any keys unless necessary
  • Photograph the screens. Minimised windows may safely be expanded and photographed. As a precaution, write down each window's contents too
  • Save screen contents to external media — a Word file to an external drive, a web page to a USB drive. If the machine has an active connection to a server with space, you can save there with the network administrator's cooperation
  • If you cannot save to external media, save to the suspect drive under a new filename, so you do not overwrite an existing file. This is not ideal and is for emergencies only
  • When closing applications, if prompted to save — do not save. Then perform an orderly shutdown
  • Note every action in your journal so you can explain it in your report
Worked example · the covert swap

An employee is suspected of writing a book on company time and saving personal files locally. His supervisors do not want him to know he is being investigated. Using imaging software you copy the hard drive onto another drive, install the duplicate in his computer, and take the original to the lab. Note what this is: not a bit-for-bit forensic copy for analysis, but a working copy so business continues, with the original preserved as evidence.

Because people notice when their desk has been touched, you photograph the scene, measure the height of his chair, and record the position of every item you have to move — then put everything back exactly. The tradecraft is as important as the imaging.

After recording, shutting down and bagging and tagging: assign one person to collect and log all evidence, minimising the number of people who handle it.

Obtaining a Digital Hash

A hash is a mathematical formula that generates a hexadecimal value based on the contents of a file, a folder or an entire drive. If a single bit or byte changes, the hash value changes. Hash before you process, hash after you process; if the two match, you have mathematical proof that the file did not change.

The algorithms, in the order they arrived

First
CRC-32

Cyclic Redundancy Check — determines whether a file's contents have changed. The most recent version is CRC-32. Not considered a forensic hashing algorithm.

Second
MD5

Message Digest 5 — the first algorithm used for digital forensics. Still widely used despite known flaws.

Third
SHA-1

Secure Hash Algorithm version 1, developed by NIST. Has slowly replaced MD5 and CRC-32.

Now
SHA-256

Newer versions such as SHA-256 are already in use, and are what you should record today.

The three rules for forensic hashes

From the work of Wang Xiaoyun and colleagues at Tsinghua University and Shandong University of Technology:

  1. You cannot predict the hash value of a file or device.
  2. No two hash values can be the same. (Collisions have occurred in research using supercomputers.)
  3. If anything changes in the file or device, the hash value must change.

Try it — change one character and watch

Live SHA-256 of your own text

Type in the box. The hash is recomputed in your browser on every keystroke. Delete a single character and compare — the new value has no visible relationship to the old one. That property is called the avalanche effect, and it is the whole reason hashing works as evidence.

Baseline— Current—
Hashes match — evidence integrity verified.

Length: 0 characters · output is always 64 hex characters (256 bits), whatever the input length.

Keyed and nonkeyed hash sets

Nonkeyed hash set

A unique hash number generated by a software tool such as the Linux md5sum command. Satisfies most forensic needs. Its advantage is that it identifies known files — executables, viruses, contraband images — that hide by changing their names. Rename the file and the extension all you like; the hash value does not move.

Keyed hash set

Created by an encryption utility's secret key. You use the key to produce a unique hash value for a file. It cannot identify files the way a nonkeyed hash can, but it produces a hash set unique to your evidence — nobody without the key can reproduce it.

When a collision is alleged

In both MD5 and SHA-1 collisions have occurred — two different files with the same hash value. They are rare, and both algorithms are still used for validating digital evidence. If a collision is suspected, settle it with a byte-by-byte comparison: the MS-DOS comp command or the Linux diff command.

In practice today

MD5 and SHA-1 are both broken for collision resistance — deliberate collisions can now be manufactured on ordinary hardware — so no new system should rely on them alone. They remain acceptable for detecting accidental change, which is why case records still carry them. Current practice records SHA-256 alongside MD5. For Indian students there is a legal edge to this: the Section 63 BSA certificate expects the hash value of the electronic record to appear on the certificate, so the hash is no longer just good practice — it is part of the document that makes the evidence admissible.

Reviewing a Case

Every digital forensics case, whatever its size, runs through the same five general tasks. Reviewing a case means walking back through them and asking what you would do differently.

TASK 1Identify the case requirementsWhat is alleged, what is in scope, what must be proved
TASK 2Plan your investigationGoal, scope, materials needed, tasks to perform
TASK 3Conduct the investigationAcquire, validate, analyse — documenting throughout
TASK 4Complete the case reportUnderstandable to a layman, technically correct, defensible
TASK 5Critique the caseThe step everyone skips. What worked, what did not, what to change next time

A sample civil investigation — the widget email

Most private-sector cases are low-level investigations, or noncriminal cases. That does not mean unimportant; it means less effort than a major criminal case.

The facts

Mr Jones at Company A claims to have received an order for $200,000 of widgets from Mr Smith, the purchasing manager at Company B. Company A manufactures them and notifies Company B they are ready. Mr Smith replies that they ordered nothing and will not pay. Company A produces an email requesting the widgets that appears to be from Mr Smith; Company B says it did not originate from their mail server. Company A sues. Both sides demand discovery on the other's computer — Company A hoping to find the original message, Company B believing the email is a fake.

You are dispatched to Company A to examine Mr Jones's computer. The discovery order authorises you to recover only his Outlook mail folder, the .pst file. Nothing else.

  1. Exit Outlook on Mr Jones's computer.
  2. Locate the .pst file in File Explorer; you may need Windows Search to find files with that extension.
  3. Check its size and connect a suitable storage device, such as a USB drive.
  4. Copy the .pst to the USB drive, then remove the drive.
  5. Fill out your evidence form — where on the disk you found the file, and the date and time you did it.
  6. Return to the lab and place the USB drive in your evidence safe.

For most civil investigations you collect only the specific items that lawyers or Human Resources have determined to be germane. Notice how much of the discipline in this list is about not doing things.

Covert surveillance in the private sector

Another common private-sector activity is covert surveillance of employees abusing their computing privileges. It must be well defined in company policy before it can be carried out — if no policy informs employees they have no privacy rights on company equipment, no surveillance can be conducted without exposing the company to civil or even criminal liability. If no policy exists, one must be created and every employee notified. The legal department should draft language appropriate to the jurisdiction.

The mechanics: real-time surveillance requires sniffing data transmissions between the suspect's computer and a network server. Network sniffers such as Wireshark show what is being transmitted. Screen-capture and keylogger programs collect screens and keystrokes and are usually disguised as other programs in Task Manager. Enterprise tools can activate agents over the network to remote workstations so examiners can work in real time through a remote connection.

A sample criminal investigation — check fraud

The facts

Because high-quality printers are now cheap, one of the most common computer-related crimes is check fraud — and many of these cases also involve manufacturing false ID cards such as driving licences. Police received a tip that a check-forging operation was running in an apartment building. After contacting a reliable informant, the detective had enough for a search warrant and asked the patrol division to help serve it. On entering and conducting a preliminary search he found a network of six high-end workstations.

That single fact — six networked machines rather than one PC — changes everything covered in Topic 13: the number of examiners needed, the storage capacity to bring, whether the machines can be seized without irreparable harm, and whether additional technical expertise is required for the server and network configuration. Which is the point of reviewing cases at all: the preparation tasks are only as good as the information you had when you did them.

The Whole Unit in Eighteen Lines

A · Analysis and Validation

01What to collectScope comes from the warrant, the discovery order or company policy. Beware scope creep; document every request to widen. Ten standard steps from wiping the target drive to maintaining control of findings.
02Validating dataHash before and after. Hex editors hash individual files and sectors; block-wise hashing finds fragments of a file that no longer exists. Two files with the same content have the same hash whatever they are named.
03Data hidingExtensions, hidden attribute, hidden partitions, clusters marked bad, bit-shifting, steganography, encryption and passwords. Five steganalysis attacks. Recovery by dictionary, brute force or rainbow table — defeated by salting.
04Remote acquisitionsConnect over the network and copy; almost always a live acquisition. An agent must be installed by trusted CD, preinstallation, or push. Five security features: password, encryption, GUIDs, trusted binaries, digital signatures.

B · Network Forensics

05OverviewCollecting and analysing raw network data to ascertain how an attack was carried out. Know your normal traffic patterns. Harden first: layered defence, and the NSA's DiD — people, technology, operations.
06Live acquisitionsNeeded because attacks may leave traces only in RAM. Results cannot be reproduced, so document everything. Six steps: test boot media, log actions, prepare storage, copy RAM, act on the incident type, hash everything.
07Standard proceduresKeep a standard installation image with hashes; fix the vulnerability; retrieve volatile data live; image the compromised drive; compare hashes against the baseline.
08Network toolstcpdump captures, Wireshark analyses and rebuilds sessions via Follow TCP Stream. Watch receiving ports above 1024. SYN flag detection catches SYN floods. Tcpslice, Tcpreplay, Etherape, Netdude, Argus, Tripwire.
09Honeynet ProjectNon-profit, three objectives: awareness, information, tools. Built to study DDoS (using zombies) and zero day attacks. A honeypot is the decoy with no real data; a honeywall monitors and records what attackers do to it.

C · Crime and Incident Scenes

10Identifying evidenceAny information stored or transmitted in digital form; courts treat it as physical evidence. Identify, collect, analyse, reproduce. Standards: ISO/IEC 27037, SWGDE, NIJ first-responder guide. In India, Section 63 BSA 2023.
11Private-sector scenesEasier because everything is under company authority — but only if a policy statement and warning banner exist, otherwise employees have an expectation of privacy. On finding a crime: assess, inform management, protect commingled data, stop.
12Law enforcement scenesProbable cause, then a warrant particularly describing place and things. Innocent information, limiting phrase. Plain view doctrine and the Horton three-prong test — increasingly rejected for digital searches.
13Preparing for a searchNature of the case, type of OS or device, whether you can seize, description of the location, who is in charge, additional expertise, tools. Initial-response and extensive-response field kits.
14Securing the sceneDefine a wider perimeter than you need. Remove everyone not investigating. Professional curiosity destroys evidence, and digital evidence has no elimination-print equivalent.
15Seizing evidenceJournal, video and stills with every cable labelled, sketch, then check power state. If off, leave it off. If on, orderly shutdown on modern systems — a first responder's judgement call because logs may be lost.
16Storing evidenceSolid-state USB is now the optimum; CDs and DVDs last only 2–5 years. Make two copies with two different tools. Restrict lab access, keep a sign-in roster, retain logs to legal requirements.
17Digital hashCRC-32 (not forensic), MD5, SHA-1, SHA-256. Three rules: unpredictable, unique, changes if anything changes. Nonkeyed identifies known files; keyed uses a secret key. Collisions settled byte-by-byte.
18Reviewing a caseIdentify requirements, plan, conduct, report, critique. Civil example: recovering only the .pst file under a discovery order. Criminal example: a check-forging operation found to be six networked workstations.
